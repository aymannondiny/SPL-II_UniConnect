# Project Teammate Finder Decisions

1. The module is a modular-MVC vertical slice under `com.uniconnect.project`. Authentication, Profile, and Notification expose service boundaries; Project does not access their repositories or entities.
2. Only an ACTIVE, non-anonymized STUDENT may create, browse, view, manage, apply, or review. Creator suspension therefore blocks management and new applications until reactivation. A pending applicant may still be rejected while suspended, but acceptance requires current student eligibility.
3. Capacity includes the creator and is constrained to 2–100. Membership count, vacancies, fullness, expiry, and availability are derived. There is no persisted FULL status.
4. `applicationDeadline` is mandatory and evaluated with an injected `Clock` in `Asia/Dhaka`. Stored lifecycle timestamps use UTC `LocalDateTime` consistently with the existing schema.
5. Default browsing contains non-expired OPEN projects, including FULL projects. Stored status and derived availability are independent filters and combine with AND. Closed/expired projects retain direct details; deleted projects return 404 from ordinary endpoints.
6. A student has one lifetime application per project. There is no withdrawal or reapplication. Pending applications survive close and expiry, but deletion changes them to `CANCELLED_PROJECT_DELETED`.
7. Acceptance locks accounts, project, then application; rechecks eligibility and membership count; and commits status, membership, audit, and notification in one transaction. Project locking also serializes capacity edits, close/reopen, and deletion.
8. Normal project actions and the privacy hook follow account-before-project lock ordering. This matches account moderation's user-row serialization while avoiding a project/user inversion. Involved account rows are locked by ascending ID.
9. Deletion is terminal and preserves projects, skills, applications, memberships, and audits. Each cancelled pending application uses a unique `project-deleted:{applicationId}` notification event key.
10. Creator department is resolved from the current profile at read/filter time. It is not copied into Project.
11. `ProjectOwnerPrivacyService` is the only account-anonymization integration surface in this milestone. It requires an existing transaction and account lock; the account workflow remains deferred.
12. V19 preserves V1–V18 migrations and every existing notification type/reference pair, then adds only project application decision and deletion notifications.
13. A project title names the recruitment listing, not necessarily a finalized project idea. Team-first listings are valid: students may form a team around an area, course, or collaboration goal and select the final topic together. The title remains mandatory.
14. `canApply` is derived for the current viewer and is advisory only. Creator, membership, lifetime-application, recruitment-state, and creator-account eligibility checks determine the flag; the application command independently enforces the same authoritative rules.
15. FR_29 candidate search is deterministic filtering, separate from the `/recommendations` endpoint. Every required skill must match; optional skills affect only the visible requested-skill intersection and never eligibility, count, order, or pagination.
16. Standalone candidate search excludes only the viewer. Owned-project search is creator-only, requires OPEN non-expired recruitment with a vacancy, and excludes current members plus every lifetime applicant before counting and pagination.
17. Candidate search reuses Discovery orchestration and Profile's privacy-aware member query. Project owns only project authorization, stored-skill selection, lifecycle checks, and project-specific exclusions. No parallel candidate persistence or cross-module repository access is introduced.
18. Skills, study year, and project availability remain protected profile details. Hidden values cannot influence predicates, counts, pagination, or response explanations. Candidate responses expose only the requested visible skill intersection and permitted navigation by user ID.
19. Skill matching and project availability are search concerns only. They do not constrain project browsing, `canApply`, or application submission.
20. Candidate search is transient and adds no migration or index. V24 extends mentorship notifications and is unrelated to FR_29; any future candidate-search index requires measured PostgreSQL evidence and a forward-only migration.
21. The project API includes a paginated applicant-owned `/applied` view so students can track lifetime application decisions and cancelled listings. Soft-deleted listings remain hidden from ordinary project detail routes.
22. Recommendations implement the approved transient FR_30 score: 70 points for weighted skill compatibility, 20 for visible shared interests, and 10 for an ACCEPTED direct connection. Required project skills have weight 3 and optional skills weight 1. Interest points divide visible shared interests by the creator's distinct normalized interests. Missing components contribute zero and their weight is not redistributed. No recommendation record is persisted.
23. Recommendation rules intentionally differ from FR_29: they accept partial required-skill overlap and optional skills contribute to scoring, while FR_29 requires all required skills and ignores optional skills for eligibility, counts, order, and pagination. Neither workflow constrains `canApply` or application submission.
24. Project Finder is intended as a first-party Flutter workspace destination. The Flutter workspace integrates open listings, creator management and review, applied history, standalone and project-context candidate search, creator-only teammate recommendations with score breakdowns, fresh project details, and PROJECT reporting.
25. Recommendation eligibility and privacy are resolved before scoring. Candidates are ranked by unrounded totals descending, then normalized name and user ID, and limited to 20 only after ranking. Arithmetic uses scale 16 and `HALF_UP`; response scores and components use two decimals with `HALF_UP`, so independently rounded components may differ from the rounded total by `0.01`.
26. Only information visible to the creator contributes to or explains a score. Connection scoring is direct-only and exposes no private path. The response preserves the existing Flutter fields and adds score components, normalized matched interests, and the accepted-direct-connection flag.
27. PROJECT is a supported content-report target. Project owns ordinary detail
    visibility and creates the reporter-visible immutable snapshot; Reporting
    stores it with the creator as owner and no parent club. Closed and expired
    projects remain eligible while accessible. ACTION_TAKEN accepts only an
    existing unreversed suspension of that creator and adds no project-removal
    authority.
